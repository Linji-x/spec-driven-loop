# Contributing to Spec-Driven Loop

Thank you for helping make specification-first delivery more reliable. Contributions may be written in Chinese or English.

## Before opening an issue

- Use **Bug report** for behavior that contradicts the documented workflow.
- Use **Feature request** for a new workflow capability or template improvement.
- Use [Discussions](https://github.com/Linji-x/spec-driven-loop/discussions) for usage questions, ideas that are not yet actionable, and show-and-tell cases.
- Remove customer names, secrets, private repository paths, and proprietary code from logs or example documents.

For a bug, include the Codex version/environment, exact invocation, expected and actual behavior, and the smallest public excerpt from the relevant `LOOP.md`. For a feature, explain the failure mode it addresses and whether it changes specification freezing, agent coordination, or main-agent acceptance semantics.

## Source of truth

`spec-driven-loop/` is the authoritative standalone skill. `plugins/spec-driven-loop/skills/spec-driven-loop/` is generated from it and must never be edited directly.

After changing the authoritative skill, run:

```powershell
pwsh -File scripts/sync-plugin-skill.ps1
python scripts/validate_repo.py
```

The pull request CI checks the same mirror invariant.

## Pull request checklist

1. Keep each change focused and explain the user-facing failure mode it solves.
2. Preserve the explicit approval gate: no production implementation before the user approves the frozen specification and acceptance contract.
3. Preserve the judge contract: agent completion reports are evidence, not acceptance.
4. Update both `README.md` and `README.en.md` when public behavior or installation changes.
5. Update or add an anonymized example when a workflow change is easier to understand from evidence.
6. Run the repository validation and include the command result in the PR.
7. Do not commit `dist/`, local credentials, private prompts, or generated marketplace caches outside the checked-in repository marketplace.

## Style

- Keep instructions direct and testable.
- Use stable IDs such as `FR-001`, `AC-001`, and `TASK-001` in durable examples.
- Mark uncertainty explicitly as `TBD`, `ASSUMPTION`, or `BLOCKED`.
- Prefer one authoritative location for each fact and link to it elsewhere.

## Release policy

Maintainers publish signed-off semantic versions from a green `main` branch. Release archives and `SHA256SUMS.txt` are generated by `scripts/build-release.ps1`. Plugin installation remains Preview until a supported environment completes the documented end-to-end marketplace test.
